# codesec-testbed

A deliberately vulnerable repository for exercising **FortiCNAPP Code Security**.
One directory per detection capability, one or two planted findings per file,
and a ground-truth manifest in [`EXPECTED-FINDINGS.md`](EXPECTED-FINDINGS.md)
so scanner output can be diffed against what is actually here.

> **This repository is a test fixture.** Nothing in it is deployed, installed or
> run. Every credential is fabricated and carries the marker `CODESECTESTBED`.
> The one CI workflow that contains real misconfigurations is guarded with
> `if: false` and never executes.

## Layout

| Directory | Capability | What is in it |
|---|---|---|
| `sca/` | SCA | Package manifests and lock files for nine ecosystems, each pinned inside a published GHSA vulnerable range |
| `sast/` | SAST | Injection, traversal and deserialisation flaws in Java, Python, JavaScript and Go |
| `sast/crypto/` | Crypto misuse | Broken hashes and ciphers, hard-coded IV, TLS verification disabled |
| `secrets/` | Secrets | Cloud keys, tokens, a database URL and a real (throwaway) RSA private key - plus one secret that exists **only in git history** |
| `iac/` | IaC | Terraform, Kubernetes, Dockerfile and CloudFormation, each misconfigured in the usual ways |
| `license/` | License | A GPL-3.0 library vendored into an Apache-2.0 project |
| `.github/workflows/` | CI/CD posture | An inert workflow carrying the standard pipeline misconfigurations, plus a working example of the FortiCNAPP CI integration |

## Design rules

Three things make this a testbed rather than a pile of bad code:

1. **Every finding is sourced.** SCA pins cite the GHSA ID, the CVE, the
   vulnerable range and the fixed version. Nothing is invented - the advisory
   data comes from <https://github.com/advisories?query=type%3Areviewed>.
2. **Clean controls sit next to dirty ones.** Several files contain the correct
   version of the same operation (`findUserSafely`, `run_backup_safely`,
   `SecureClient`, `aws_s3_bucket.compliant`, the hardened Deployment). A scanner
   that flags those is over-reporting, and that is worth measuring too.
3. **Lock files are real.** `sca/npm/package-lock.json` and `sca/go/go.sum` were
   generated by the real tools, so transitive resolution is exercised rather
   than just top-level manifest parsing.

## Running a scan against it

```bash
git clone https://github.com/lacework-dev/codesec-testbed
cd codesec-testbed

lacework component install sca
lacework sca scan ./ -f lw-json -o /tmp/scan.json

lacework component install iac
lacework iac scan -d ./iac
```

To exercise the hosted path instead, connect the repository through
**Settings -> Code security -> Integrate code scanning** and pick the Git
provider integration.

### In CI

`.github/workflows/` carries the official `lacework/code-security-action`
integration in both modes. `lacework-code-security-pr.yml` scans the head and
its parent on every pull request and comments the alerts the PR introduces;
`lacework-code-security-push.yml` scans `main` on push and on a daily cron,
and is the one that populates the repository's branch view under
*Investigation -> Code security -> Repositories*. Without the push workflow
the repository never shows up there at all.

Both need `LW_ACCOUNT`, `LW_API_KEY` and `LW_API_SECRET` as repository or
organisation secrets (plus `LW_SUBACCOUNT` where sub-accounts are in use).
`LW_ACCOUNT` is everything to the left of `.lacework.net` in the console
hostname, which for a non-production environment is more than one label:
`dev5qatest.dev5.corp.lacework.net` means `LW_ACCOUNT=dev5qatest.dev5.corp`.

## What it deliberately does not cover

Container images and hosts. Those are not repository surfaces; they belong to
the platform Vulnerability module, not to Code Security.
